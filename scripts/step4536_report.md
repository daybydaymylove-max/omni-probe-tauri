# Omni-Probe 对标国际顶级开源项目细化功能与算法硬核审查评估报告

本报告严格遵循**反自嗨、去情绪化与工业级严谨原则**，将 Omni-Probe 当前所有底层算法、协议引擎、安全审计与前端渲染模块，逐项横向对标全球工业界与开源界的统治级标杆项目（**Wireshark、Zeek、Suricata、mitmproxy、Sniffnet、PulseView**）。

通过深入代码实现层面的解剖，全面梳理我们在技术深度、吞吐极限、协议覆盖与算法鲁棒性上的**真实短板与技术代差**，并给出严谨的定量打分（1~10 分制）。

## 二、细化功能与算法逐项解剖及短板清单

### 1. 抓包引擎与物理网卡接口（对标：Wireshark dumpcap / libpcap / PF_RING）
- **标杆水准**：
  - Wireshark 依赖独立的 `dumpcap` 专属捕获进程，底层基于 Linux `PACKET_MMAP` 或 Windows Npcap 内核环形缓冲区实现 Zero-Copy（零拷贝），可承受 10Gbps 万兆线速且丢包率 $< 0.001\%$；
  - 支持纳秒级（Nanosecond）硬件时间戳。
- **Omni-Probe 现状与短板**：
  1. **IPC 序列化瓶颈**：当前通过 Tauri 的 `app.emit()` 将报文打包成 JSON 推送至 WebView2。当捕获速率超过 $5,000 \sim 10,000 \text{ pkts/s}$ 时，JSON 序列化与 IPC 跨进程传输直接占满单核 CPU，产生明显数据积压；
  2. **平台绑定受限**：深度依赖 Windows Npcap 动态链接库，缺失 Linux 原生 `AF_PACKET / eBPF / XDP` 捕获驱动，缺失 macOS BPF 原生支持；
  3. **时间戳精度**：仅支持操作系统微秒级软件时间戳，无网卡硬件时间戳对齐能力。

---

### 2. TCP 流重组与状态机算法（对标：Zeek / Suricata Flow Engine）
- **标杆水准**：
  - Zeek 与 Suricata 拥有数十万行经受全球主干网洗礼的流重组引擎，完整实现 RFC 793/1323 状态转移矩阵；
  - 能够完全免疫针对网络入侵检测系统的**重叠反躲避攻击（TCP Overlapping / Evasion Attacks）**，如针对新旧载荷不一致时的优先级裁剪算法（BSD / Linux / Windows 差异化重叠裁决策略）。
- **Omni-Probe 现状与短板**：
  1. **状态机精细度不足**：目前基于四元组哈希与 `Seq` 顺序重组，但缺少针对 SYN Flood、乱序 FIN/RST 双向重叠的完整状态追踪；
  2. **恶意重叠攻击防御脆弱**：当攻击者故意发送相同 `Seq` 但载荷不同的分节进行混淆时，目前重组逻辑尚未实现对目标操作系统协议栈特性的指纹拟合；
  3. **并发流会话表老化策略**：在超大规模并发连接（如同时存在 $> 20,000$ 个活动 TCP 连接）时，流重组哈希表的内存回收机制偏粗糙，存在内存增长不可控的隐患。

---

### 3. 协议深度解包器（DPI）（对标：Wireshark Dissectors）
- **标杆水准**：
  - Wireshark 积淀近 30 年，拥有全球最庞大的协议知识库（支持 3,000+ 协议），对每一个协议支持位域（Bitfields）、TLV（Type-Length-Value）逐层展开、枚举映射及动态 Display Filter 语法编译器。
- **Omni-Probe 现状与短板**：
  1. **协议覆盖数量级差距**：Omni-Probe 覆盖了 Modbus、S7comm、EtherCAT、DNP3、IEC 60870-5-104、SL651、HJ212 及长尾工控插件等约 15~20 种主流协议，**协议覆盖广度仅为 Wireshark 的 $0.5\%$**；
  2. **私有加密与长尾版本缺失**：如西门子最新的加密协议 S7Plus（基于 TLS/OMSPC 加密）、施耐德深度私有函数、Rockwell CIP 安全变种未完全实现逆向解包；
  3. **过滤语法树未编译器化**：目前的过滤条件主要依靠字符串检索或预设字段匹配，尚未建立类似于 Wireshark `ip.src == 192.168.1.1 && (s7comm.param.func == 0x05 || modbus.func_code == 3)` 的词法分析器（Lexer）与语法树编译器（AST Parser）。

---

### 4. TLS 流量解密与透明代理（对标：mitmproxy / Wireshark SSL Engine）
- **标杆水准**：
  - mitmproxy 支持动态 CA 证书静默注入系统受信任根证书库，支持完整的 HTTP/1.1、HTTP/2、HTTP/3 (QUIC) 双向透明代理与 WebSocket 流量拦截篡改；
  - Wireshark 支持导入 `SSLKEYLOGFILE` 后秒级解密 TLS 1.2/1.3 所有通用密码套件。
- **Omni-Probe 现状与短板**：
  1. **密码套件覆盖不全**：当前虽然支持 TLS 1.2 PRF 与 TLS 1.3 HKDF 密钥派生，但仅实现了基于 `AES-128-GCM` 的对称解密，**未实现 `ChaCha20-Poly1305`、`AES-256-GCM` 及 SM4-GCM 国密套件**；
  2. **不支持下一代 QUIC / HTTP/3**：对基于 UDP 传输的 QUIC 流量完全无法被动还原；
  3. **系统根证书信任未完全自动化**：代理模式下，自签名证书未实现基于 Windows CryptoAPI（CertAddCertificateContextToStore）的静默受信任安装，操作门槛较高。

---

### 5. 物理外设多维总线（对标：sigrok / PulseView / USBPcap）
- **标杆水准**：
  - sigrok 支持百兆/千兆采样率的逻辑分析仪纳秒级波形解码；
  - USBPcap 依赖底层 Windows 过滤驱动，能够捕获主机控制器上每一个 USB 端点（Endpoints）发出的原始 URB（USB Request Block）比特流。
- **Omni-Probe 现状与短板**：
  1. **USB 抓包停留在应用层事件**：目前通过 Windows SetupAPI / WMI 监听设备插拔生命周期和枚举静态描述符树（Descriptor Tree），**未内嵌内核驱动，无法实时抓取 USB 鼠标击键、U盘裸扇区读写的微秒级传输报文**；
  2. **串口时间精度局限**：串口目前基于 Windows Win32 API 异步读取，时间戳粒度在毫秒级，无法像示波器/逻辑分析仪一样进行波形边缘（Edge/Jitter）微秒级抖动分析。

---

### 6. 入侵检测与基线学习算法（对标：Suricata / Snort / Zeek Anomaly）
- **标杆水准**：
  - Suricata 采用 Intel Hyperscan 多模式超大规模正则匹配引擎，能在千兆流量中并行匹配数万条活跃恶意特征（Emerging Threats）；
  - 具备时序流量马尔可夫链和孤立森林（Isolation Forest）异常流量分类器。
- **Omni-Probe 现状与短板**：
  1. **缺乏底层硬件加速匹配库**：目前规则库匹配依靠 Rust 标准正则与哈希遍历，规则容量在数百条时性能尚可，若直接导入万级规则，匹配时延将呈线性下降；
  2. **统计学算法模型偏单维**：目前的基线学习算法采用滑动时间窗口内的均值（$\mu$）与标准差（$\sigma$）（Z-Score 阈值检测），**未引入多维时空自关联模型**，容易在工控设备昼夜周期切换或排产变更时产生误报。

---

### 7. 司法取证与数据防篡改链（对标：Autopsy / FTK Imager / RFC 3161）
- **标杆水准**：
  - 司法级电子数据取证要求全流程链式哈希固化，且必须结合国家授时中心或权威第三方数字证书认证中心（CA）的 RFC 3161 远程网络时间戳签名，确保法庭采信的排他性。
- **Omni-Probe 现状与短板**：
  1. **缺少权威远程时间戳（TSA）公证**：当前的 SHA-256 证据链在本地闭环完备，但时间戳基于系统本地时钟，未引入公钥密码基础设施（PKI）签发的外部权威证据链；
  2. **取证格式标准局限**：导出目前主要为通用 PCAP 格式，未支持包含司法注释、捕获网卡硬件信息及接口丢失统计的标准 PCAPng 结构化元数据块（Enhanced Packet Block Comments）。

---

### 8. 大数据承载力与极端吞吐性能（对标：Wireshark C++ Native / Sniffnet Iced）
- **标杆水准**：
  - Wireshark 基于原生 C++ 紧凑内存布局，分析几百万个数据包仅占用几百兆内存；
  - 拥有成熟的文件分段流式存储与磁盘外存映射机制，内存不会随时间无限膨胀。
- **Omni-Probe 现状与短板**：
  1. **V8 垃圾回收（GC）与对象开销**：前端基于 Vue 3 响应式系统，每一个前端报文都是一个完整的 JavaScript Proxy 对象。当累积解析超过 100,000 帧报文时，浏览器内存占用会攀升至 1GB 以上，偶发触发 V8 引擎的长时 GC 暂停；
  2. **未引入流式持久化写盘**：当前抓包数据主要驻留在内存环形缓冲池（Ring Buffer 默认 64MB），超出时采用先进先出覆盖，缺少像 `dumpcap` 那样的自动化按时间/大小切片分卷无损落盘机制。

## 三、硬核总结与差距弥合路线图（Roadmap to Elite）

客观而言，Omni-Probe 目前的优势在于：**在工控 OT、硬件外设（COM/USB）与本土等保三级合规这一特定交叉赛道上，提供了全球开源界几乎唯一的现代液态全息交互界面与一体化工作台体验**。

但若要真正达到世界一流网络安全工具的硬核深度，必须刮骨疗伤，分阶段攻克以下四大核心工程难关：

1. **引擎重构（解绑 IPC 瓶颈）**：将核心抓包、重组与规约解析彻底下沉至独立后台 Daemon，前端仅订阅高频汇总指标，报文详情按需惰性懒拉取，切断大流量下 IPC 传输瓶颈；
2. **多平台无损驱动层抽象**：抽象跨平台捕获接口，在 Linux 上引入原生 `AF_PACKET` 环形映射与 eBPF，在 Windows 上深化 Npcap 零拷贝内核配置；
3. **协议解包深度与 AST 语法树编译器**：构建标准 AST 表达式解析器，替代简单文本过滤；为工控协议补充深度位域定义与长尾变种；
4. **引入内核级 USB 抓包与专业时间戳**：结合开源 USBPcap 驱动接口，将 USB 审计由应用层插拔事件推进一步至端点 URB 裸包级捕获。
